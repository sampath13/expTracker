# S3.3: Receipt Field Parsing

**Epic:** 3 — OCR Pipeline
**Depends-on:** S3.2
**Priority:** HIGH

## Context
Transform raw PaddleOCR text blocks into structured receipt data. This is the most complex parsing step — receipt formats vary widely across Singapore's grocery chains. The parser must identify: retailer name (from receipt header), purchase date, individual line items (name, quantity, unit, price), and totals (subtotal, GST, grand total). Indian provision shops often use non-standard formats requiring a fallback parser.

## Scope
- Four parsing modules: retailer extraction, date parsing, line item parsing, totals extraction
- Retailer: matched against known chain keywords (NTUC, Sheng Siong, Cold Storage, etc.); address text for outlet detection; fallback: largest-font text block
- Date: regex patterns for DD/MM/YYYY, DD-MM-YYYY, DD Mon YYYY, YYYY-MM-DD; located in header or footer
- Line items: price pattern detection ($X.XX or X.XX), quantity extraction (1 X, 2X, QTY:2), unit detection from product description (e.g., "600G" → 600g)
- Totals: subtotal, GST, grand total from receipt footer using keyword matching
- Fallback parser for non-standard receipts (Indian provision shops): simple line-by-line parsing, minimal structure
- Orchestration function that combines all four parsers into a single structured output
- **Out of scope:** Template-based parsing per retailer, ML-based parsing

## Acceptance Criteria
1. Retailer name correctly extracted from NTUC, Sheng Siong, Cold Storage receipts
2. Date parsed from multiple formats
3. Line items extracted with name, qty, unit, unit_price, total
4. Subtotal, GST, total identified from receipt footer
5. Full pipeline returns complete structured dict
6. Non-standard receipt (Indian provision shop) falls back gracefully
7. Empty text blocks list returns default values without error
8. Tests cover at least 3 different receipt formats
